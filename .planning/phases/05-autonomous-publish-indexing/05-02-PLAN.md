<plan_context>
## Phase Boundary Context
Phase 5 establishes zero-human-gated publishing.
Plan 05-02 builds the scheduled publishing engine and concurrency/failure resilience mechanisms:
1. **Idempotent Claim-by-Hash Locking (D-02):** Cryptographic SHA-256 fingerprint lock prevents dual-publishing during overlapping cron runs or retries.
2. **Dead Letter Queue (DLQ) & 3-Strike Isolation (D-03):** Transient failures are tracked in `content/keywords/dlq.json`; persistent failures ($N \ge 3$) are isolated to `content/quarantine/` with `'publish_dlq_exhausted'` without stalling future publishes.
3. **GitHub Actions Engine (D-01):** Scheduled workflow running 3–4 posts/week (Mon, Wed, Fri, Sun at 06:00 UTC) with git commit & push to `master`, triggering Vercel edge deployment.

## Decisions Handled
- **D-01:** GitHub Actions Execution Engine (`.github/workflows/publish.yml`, 4x/week schedule at 06:00 UTC, `contents: write`, git push to `master`).
- **D-02:** Idempotent Claim-by-Hash Lock (SHA-256 hash in `content/keywords/pipeline-state.json` under `activeClaim`).
- **D-03:** Dead Letter Queue (DLQ) (`content/keywords/dlq.json`, 3-strike rule exhausting to quarantine).
</plan_context>

<action>
1. In `lib/pipeline/types.ts`:
   - Extend `RegistryStage` to include `'published'`:
     ```typescript
     export type RegistryStage =
       | 'expanded'
       | 'filtered'
       | 'briefed'
       | 'outlined'
       | 'drafted'
       | 'quarantined'
       | 'published'
       | 'rejected';
     ```
   - Add `publishedAt?: string` to `RegistryEntry` (or within `publish?: { publishedAt: string; liveUrl: string }`).
   - Extend `PipelineState` in `lib/pipeline/qa/circuit-breaker.ts` (or `types.ts`) with:
     ```typescript
     activeClaim?: {
       hash: string;
       entryId: string;
       claimedAt: string;
     };
     ```
2. In `lib/pipeline/registry.ts`:
   - Update `assertTransitionStage` to permit transition from `'drafted'` to `'published'`.
   - Update `validateEntry`: if `e.stage === 'published'`, verify `e.draft?.slug` and `e.qa?.passedAt` are present.
3. Create `lib/pipeline/publish/claim-lock.ts`:
   - Function `computeClaimHash(candidateId: string, candidateUpdatedAt: string): string`:
     - Returns `crypto.createHash('sha256').update(`${candidateId}:${candidateUpdatedAt}`).digest('hex')`.
   - Function `acquireClaimLock(candidateId: string, candidateUpdatedAt: string, keywordsDir?: string): { success: boolean; hash: string; reason?: string }`:
     - Reads `pipeline-state.json`.
     - If `activeClaim` exists:
       - Check age: `Date.now() - new Date(activeClaim.claimedAt).getTime()`.
       - If age < 30 minutes (1800000 ms):
         - Return `{ success: false, hash: activeClaim.hash, reason: `Already claimed by entry ${activeClaim.entryId} at ${activeClaim.claimedAt}` }`.
       - If age >= 30 minutes:
         - Log warning: `Stale claim lock detected (>30m), overriding`.
     - Write new claim: `{ hash, entryId: candidateId, claimedAt: new Date().toISOString() }` to `pipeline-state.json`.
     - Return `{ success: true, hash }`.
   - Function `releaseClaimLock(hash: string, keywordsDir?: string): void`:
     - Reads `pipeline-state.json`.
     - If `activeClaim?.hash === hash`, removes `activeClaim` and writes back.
4. Create initial tests in `tests/publish-claim-dlq.test.ts` verifying claim generation, conflict rejection, and lock release.
</action>

<task id="05-02-02" wave="2">
<description>
Implement Dead Letter Queue (DLQ) management with 3-strike quarantine escalation, CLI scheduled publisher script, and GitHub Actions scheduled workflow.
</description>
<action>
1. Create `lib/pipeline/publish/dlq.ts`:
   - Export interfaces `DlqEntry` and `DlqState`.
   - Function `recordDlqFailure(entryId: string, silo: string, error: string, keywordsDir?: string, quarantineDir?: string): { exhausted: boolean; attempts: number }`:
     - Reads or initializes `content/keywords/dlq.json`.
     - Finds or creates entry: `{ entryId, silo, attempts: 1, firstFailedAt: now, lastAttemptAt: now, lastError: error }`.
     - If existing, increments `attempts`, updates `lastAttemptAt` and `lastError`.
     - If `attempts >= 3`:
       - Invokes `quarantineDraft` with rule `'publish_dlq_exhausted'` and score `attempts`.
       - Updates entry's registry stage to `'quarantined'`.
       - Records failure in circuit breaker.
       - Appends notice to `content/quarantine/ALERT.md`.
       - Writes updated `dlq.json`.
       - Returns `{ exhausted: true, attempts }`.
     - Writes updated `dlq.json` and returns `{ exhausted: false, attempts }`.
   - Function `clearDlqEntry(entryId: string, keywordsDir?: string): void`:
     - Removes entry from `dlq.json` upon successful publishing.
2. Create `scripts/publish-scheduled.ts`:
   - Scans all `content/keywords/*/registry.json` for candidates where `stage === 'drafted'` and `qa?.passedAt` is defined.
   - Filters out entries already in `dlq.json` with `attempts >= 3`.
   - Sorts candidates FIFO by `qa.passedAt` ascending.
   - If a CLI argument `candidateId` is provided, selects that candidate specifically.
   - If no candidates available: logs `[publish] No QA-passed drafts waiting to publish.` and exits cleanly with 0.
   - Picks top candidate.
   - Attempts `acquireClaimLock(candidate.id, candidate.updatedAt)`. If failed, logs error and exits with 0 (skips duplicate execution).
   - Try publishing block:
     - Transition registry stage to `'published'`, set `publishedAt: new Date().toISOString()`.
     - Commit registry shard.
     - Call `dispatchDualTrackIndexing({ postUrl, slug, sitemapUrl, siteUrl })`.
     - Call `clearDlqEntry(candidate.id)`.
     - Call `releaseClaimLock(claimHash)`.
     - Log success: `[publish] Successfully published ${candidate.id}`.
   - Catch error block:
     - Log failure.
     - Call `recordDlqFailure(candidate.id, candidate.silo, err.message)`.
     - Call `releaseClaimLock(claimHash)`.
     - Exit with code 1.
3. Create `.github/workflows/publish.yml`:

<threat_model>
### Threat Ref T-05-03: Race Conditions & Concurrent Publishing Collisions
- **Threat:** Overlapping GitHub Actions workflow runs or retries fire simultaneously, picking the same candidate and creating duplicate git commits or colliding deployments.
- **Mitigation:** The publisher derives a deterministic SHA-256 fingerprint from `candidateId` and `candidateUpdatedAt`, locking `activeClaim` in `content/keywords/pipeline-state.json`. If a lock exists and is younger than 30 minutes, incoming executions exit immediately without touching content or git.
- **Verification:** Unit test `tests/publish-claim-dlq.test.ts` simulates concurrent workers attempting to claim the same candidate; only the first acquires the lock while the second receives an explicit rejection.

### Threat Ref T-05-04: Poison-Pill Draft Infinite Publishing Loop
- **Threat:** A malformed draft repeatedly fails during publishing execution, hanging CI workflows or re-attempting indefinitely.
- **Mitigation:** The Dead Letter Queue (`content/keywords/dlq.json`) logs every failure with timestamp and error message. On the 3rd consecutive attempt, the entry is automatically quarantined via `quarantineDraft`, registry stage changed to `'quarantined'`, circuit breaker failure recorded, and entry permanently removed from publishing rotation.
- **Verification:** Unit test `tests/publish-claim-dlq.test.ts` executes 3 simulated failures on an entry, verifying it transitions to quarantine and updates `ALERT.md`.
</threat_model>
